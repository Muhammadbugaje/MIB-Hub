## 2. Where destinations, objectives, location ids and markers are written

The guide's rule (§4.1) is one source; today there are many writers and several readers that each decide a little.

**Writers (data)**

1. `D.PLACES` in `samaru-data.js` and the generated `fslg-map.js` (place ids and marker positions; `Z.placeList` adds `mx/my`).
2. Story steps: `place`, `at`, `npc`, `route`, `routine.at`, `where`, `giver` in `fslg-story-y1..y5.js`, `-side.js`; the
   retired m1–m36 and goals in `samaru-data.js:205-385`.
3. `tools/story/build_y1.py`: the generator **chooses** places: `last_place` fallback for `find`/`collect`/`look`/photo
   beats (`:246-248`, `:327`, `:350-372`). This is where m1/m4 went to the gate.
4. The scripts `docs/story/scripts/*.md` (`[go: x]`, `[find: item at x]` tags, and prose that names places).
5. NPC homes: `at` on every `D.NPCS` entry and in each story file's `npcs`, patched by `patch:` blocks.
6. Token and alias tables in the engine: `ST.tok` (`@roomie`, `@hostel`, `@dept`, `@hostelshop`, `@super`, `@place`…,
   `samaru-story.js:66-84`) and `PLACE_ALIAS` (`:86`, stand-ins such as `oldcampus → checkpoint`).
7. Engine defaults: `Z.target` picks a place for step types without one (`samaru-core.js:142`: `sleep → @home`,
   `race → club`, `buy → market`, `ride plane → strip`, `keke → gate`); `Z.stepStart` places the find item 16–32 m
   from the place; `collect` scatters 6–46 m (`samaru-story.js:257`).
8. `ST.applyRoomie` rewrites `n.at` in `D.NPCS` at run time (`samaru-story.js:531`).
9. Other modules write the arrow target directly: `samaru-life.js:246` (timetable "follow" mode), `samaru-water.js:303`
   (swim race gates), `samaru-interior.js:302` (inside: none), `samaru-intro.js:475` (film: none), `FSLGCoop.target()`,
   jobs (`P.job.a/b`), dates (`Z.date.spot`), waypoints (`samaru-map.js:173-186`, `samaru-life.js:223`, `samaru-water.js:289`).
10. Walkthrough cards (`samaru-guide.js`) say "ride to the fountain" etc.; `docs/story/ENGINE.md §7` keeps a second
    hand-written list of place ids.
11. Dialogue lines name places in prose (`lines`), as do step `text` and mission `intro`.

## 3. Duplicate or conflicting systems

1. **Two Year 1s.** The old m1–m36 still ship in `samaru-data.js:205-385` (~180 lines) and are cut out at start-up by
   `ST.merge` when `replaceYear1` is set (`samaru-story.js:25`); `ST.oldY1` keeps them for save migration. Plus the 20
   legacy long goals g1–g20 (`D.MISSIONS` with `side: true`) beside the new side missions s1–s50.
2. **Two places for the same building**: `chemeng` and `dept_chem`; stand-in aliases (`PLACE_ALIAS`) map nine script
   places onto other buildings.
3. **Two "find" spawners**: `Z.stepStart` for `find` (core) and `nextPick` for `collect` (story); different radii, and
   only the second keeps state (unsaved) in `ST.ctx`.
4. **Two start-of-game tutorials**: the walkthrough (`samaru-guide.js`, 14 cards) and m1's own steps; both point the
   arrow (guide reads `Z.target`).
5. **Two spawn paths for people**: core spawns every `D.NPCS` entry at its `at`; `ST.applyRoomie` moves them; interiors
   bring hostel people into rooms; encounters spawn `$who`/`$other`; the intro spawns temps; city/crowd spawn walkers.
   Retired people are hidden once only (`samaru-story.js:232`), so Big Sly returns after a load (KI-016).
6. **Two save versions**: `P.v = 2` (`S.migrate` fills defaults) and `story.ver = 2` (real migrations, `ST.MIGRATIONS`).
7. **Two config sources**: the fallback `D.CONFIG` in `samaru-story.js:11` and `samaru-overrides.js` (`window.FSLG.cfg`).
   Text resolution exists twice: `Z.text` (story) and `FSLG.resolveText` (overrides); the HUD uses neither.
8. **Two quest-ish runners**: story steps (`S.missionEvent` + `ST`) and the co-op referee (`FSLGCoop`), each with a target.
9. **Monkey-patch chains instead of an event bus**: `Z.update` is wrapped by 14 files, `Z.begin` by 9, `Z.draw` by 7,
   `Z.target` by 6, `Z.emit` by 5, `Z.place` by 3. Order depends on the script list; every wrapper is a place where
   guide, map and HUD can diverge.
10. **Test harness list vs catalogue deps**: `samaru_harness.js` does not load `samaru-overrides.js` (KI-018).
11. **Stale bundle vs sources** (KI-017).

## 4. Globals and shared mutable state

Globals: `window.SamaruGame` (Z, everything), `SamaruSim` (S), `SamaruData` (D), `SamaruMap`, `SamaruDraw`, `FSLG`
(overrides), `FSLGCoop`, `GAME`/`Arcade` (arcade shell).

Mutable state, all reachable from anywhere through `Z`: `Z.P` (the save object), `Z.me`, `Z.npcs`, `Z.peds`, `Z.traffic`,
`Z.cars`, `Z.foes`, `Z.guards`, `Z.quest`, `Z.waypoint`, `Z.lastPlace`, `Z.route`, `Z.race`, `Z.date`, `Z.inside`,
`Z.blackout`, `Z.hideHud`, `Z.r3` (camera), `ST.ctx` (per-step runtime, **not saved**), `ST.queue` (dialogue),
`Z.intro.on`. Data that is mutated at run time: `D.MISSIONS` (merged, old Year 1 spliced out), `D.NPCS` (patched,
retired, `at` rewritten by `applyRoomie`, overrides), `D.ITEMS`, `D.CONFIG`, `S.RULES` (water and wild add keys).
Randomness: `Math.random` in the 3D car picker (`samaru-3d.js:407`) and elsewhere; the sim uses `S.hash`/`S.rng`
seeded by day and step, which is why the bots are repeatable.

## 5. Save format and versioning

`api.store("fslg-save", P)` (`samaru-core.js:56-57`); autosave every 15 s and at mission end. `P` is the whole player
(~1.5 KB fresh): position, money, xp, `m: { active, step, n, done }`, `flags`, `inv`, `friends`, `story` block, guide,
life, pockets. Versions: `P.v = 2` set by `S.migrate` (`samaru-sim.js:301`), which only fills missing fields from a new
player; `P.story.ver = 2` (`ST.SAVE_VERSION`, `samaru-story.js:546`) with `ST.MIGRATIONS[1]` = the Year 1 rewrite (restart
the current mission, pay ₦300 + 120 XP per step done). No top-level `saveVersion`; the key contains the initials. Not
saved: `ST.ctx` (collect items left, tail/escort state), `Z.quest`, `Z.lastPlace`. The replay bot saves and reloads at
all 92 steps of m1–m10: the step and the count survive everywhere; the item marker of a `collect` does not (KI-014).

   `fslg_credits` views (`templates/games/_settings_nav.html:8-10`) and `samaru-overrides.js`. It needs: one config

   manifest), validation (length, characters, initials 1–6), and the game reading `FSLG.cfg()` everywhere.
3. **Signs**: already runtime canvas text on planes, so they can become sign slots cheaply: move the `spots` list from
   `samaru-3d.js:108` into level data (`signSlots: { place, size, style, field }`), draw from `FSLG.cfg()`, auto-fit, and
   regenerate the textures on a "config changed" event.
